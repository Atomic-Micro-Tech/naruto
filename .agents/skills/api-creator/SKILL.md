# API Creator

Use this skill when implementing or changing Go backend features in this project. Follow the user's requested scope and the applicable API specification, database schema, business rules, and backend technical documents. The specification describes a contract; it does not imply that an endpoint or dependency is already implemented.

## Backend directory layout

Use `backendexample/` at the repository root as the folder-layout reference. Create the directories relevant to the requested backend work at the root of the target backend Go module, beside `go.mod`; preserve the reference directory names. For the aggregator this is `agregator-backoffice/backend/`. Do not copy application code or assume the example contains implementations. In addition to the reference, create `server/` for server implementations and `middleware/` when common middleware is needed.

- `cmd/`: executable entry points; `worker/`: background processing implementation.
- `server/`: implement each application server in a separate CamelCase Go file named for its protocol; put the HTTP server in `server/HttpServer.go`. Create and configure the server with injected configuration and handlers, and implement startup and graceful shutdown there. Keep `cmd/` as the executable entry point that initializes dependencies and invokes the server lifecycle. Keep route registration in `routes/Routes.go`, middleware in `middleware/Middleware.go`, and business logic in use cases; do not move those responsibilities into the server file. Coordinate shutdown with `internal/Connection.go` so active work stops before database connections close.
- `configs/`: `config.json` and safe example configuration; keep secrets out of version control. Use the loading function and main configuration struct in `internal/Config.go`, together with related component-specific structs in `internal/`.
- `telemetry/`: place OpenTelemetry setup and lifecycle code in this directory at the backend module root, for example `agregator-backoffice/backend/telemetry/Telemetry.go`; do not place the implementation under `internal/telemetry/`. Keep telemetry configuration structs in `internal/Telemetry.go` and compose them in `internal/Config.go`. In the telemetry setup file, define a shared exported package-level `Tracer` initialized with `otel.Tracer("<module-name>")`, following `testbackend/telemetry/Telemetry.go`. The instrumentation scope name must exactly match the module path declared by the target project's `go.mod`; for example, module `backendtest` uses `var Tracer = otel.Tracer("backendtest")`. Use this shared `telemetry.Tracer` when starting application spans, including controller spans, and propagate the resulting context. Initialize the provider, exporter, and shutdown lifecycle in the same telemetry package without placing secrets in span attributes. The entry point initializes telemetry after database connections and shuts it down during application shutdown.
- `middleware/Middleware.go`: implement common HTTP middleware, such as authentication, authorization, request context, and shared error handling, as needed. Each protected route passes its next handler through middleware; after successful middleware checks, call the next handler that invokes the controller. On failure, stop the chain and do not call the controller. Do not put route registration, business logic, or SQL here. All authorizer construction, authentication, scope/role decisions, and operator/provider scope enforcement belong in the middleware layer, not `routes/Routes.go`. Routes only register the method/path and pass the named controller handler to the common middleware; do not branch on `authorizer != nil`, select required scopes, or omit protected routes in the route file. Initialize required authorizer dependencies before serving and fail startup explicitly when they are missing; do not silently leave a route unregistered. Within middleware, derive the authorization policy from the HTTP method and a trusted canonical matched route pattern or equivalent explicit operation identifier, and verify the requested resource scope before invoking the controller. Maintain explicit public-route policy for endpoints such as health checks; unknown or unmapped protected operations fail closed. Avoid trusting client-supplied identity, scopes, or route identifiers. Test authorized, unauthorized, cross-tenant, missing-policy, missing-dependency, and public-route cases, and ensure failed checks never call the controller.
- `routes/Routes.go`: group route registrations by their OpenAPI tag within this file, keeping all operations of the same tag together and using a short tag comment to identify each group. For operations with multiple tags, use the same primary business tag chosen for their use-case interface and implementation. Keep all route registrations in `routes/Routes.go` rather than creating separate route files per tag. Register all HTTP routes in this file at the backend module root (for the aggregator: `agregator-backoffice/backend/routes/Routes.go`) and wire each route as `routes → middleware → controller`; `controller/`: decode and validate input, invoke the use-case interface, and select the HTTP status; `view/`: response representations and HTTP response rendering. Follow the structure of `NewRoutes` in `testbackend/routes/Routes.go`: define `NewRoutes` in this file, create an `http.ServeMux`, register each method and path with its named controller handler, and return `otelhttp.NewHandler(mux, "/")` as an `http.Handler`; declare the return type so the Go code compiles. Initialize required middleware dependencies outside the routes file and fail startup if they are unavailable. The example illustrates structure only: use the correct method, path, and handler from OpenAPI, and wrap protected routes in authentication, authorization, and tenant-scope middleware before the controller. Do not add generic route adapters or anonymous controller functions. Configure instrumentation so telemetry propagates correctly, keeps the existing error-only/full tracing policy, and does not record secrets or sensitive input.
- Every implemented HTTP route and method must be wired to a controller handler in `controller/`; create or reuse an appropriately named controller handler function for each operation, including utility routes and fallback handling for unmatched requests when implemented. The route file registers and wires handlers only; it must not contain the endpoint's inline controller logic or directly return an endpoint response. Apply common middleware before the controller, including appropriate checks for protected routes. If middleware rejects or fails a request, it must stop the chain and render its response through `view/` without calling the controller. Controllers render all of their own response paths through `view/` and use the associated use-case interface when the operation has business logic.
- `usecase/<Tag>Case.go`: implement each OpenAPI tag in a CamelCase file directly under the backend root `usecase/` package. For tag `Partners`, use `usecase/PartnerCase.go` and declare its interface and related request, parameter, and result structs in `internal/Partner.go`. Use a consistent singular domain name when deriving the file stem; group operations of the same tag in that file rather than a tag subdirectory. This requirement applies to every tag in the API specification being implemented, including tags added later, not only `Partners`. For `admin-and-operation.yaml`, map the tags as follows: `AccessKeys` → `AccessKey`, `Wallet` → `Wallet`, `Reports` → `Report`, `Dashboard` → `Dashboard`, `Sessions` → `Session`, `UserAdministration` → `UserAdministration`, `Partners` → `Partner`, `Transactions` → `Transaction`, `Cases` → `Case`, `Reconciliation` → `Reconciliation`, `Billing` → `Billing`, `Approvals` → `Approval`, and `Audit` → `Audit`. For each mapped stem, place the interface in `internal/<Stem>.go` and the implementation in `usecase/<Stem>Case.go`; apply the same naming convention to every tag in other applicable specs. Implement each operation of each tag within the authorized scope and report incomplete work, rather than creating empty placeholder files. Every use-case implementation must have a constructor that requires a non-nil `context.Context` and any required non-repository dependencies, for example `NewPartnerUseCase(ctx context.Context, ...)`. Instantiate it for each request or operation with the caller's actual context. Inside each use-case function, create each model repository only when it is needed by calling its constructor directly, for example `operatorRepo, err := repo.NewOperatorRepo(usecase.ctx)`, and handle the constructor error before use. Do not construct all repositories eagerly in the use-case constructor, main, controller, or a use-case wiring factory and inject repository instances into the use case. Continue to use the caller context when constructing repositories and invoking other context-aware dependencies. Preserve cancellation, deadlines, trace propagation, and transaction scope; do not reuse a request-bound use case across requests, retain it after cancellation, or substitute `context.Background()` for the caller's context. Keep interface method signatures consistent with the applicable contract and existing callers; a constructor context requirement alone does not require removing context parameters from existing use-case methods. Test context propagation and cancellation through the use case and its dependencies. Before implementing the use case, create representative mock data based on the operation’s OpenAPI request, response, and schema in `usecase/MockData.go`, using tag-specific names to avoid collisions. Define the corresponding use-case interfaces in the backend root `internal/` package, using CamelCase Go filenames. Inside each controller operation, after request validation, construct the needed use case directly with its constructor and `request.Context()`; for example, `partnerUseCase, err := usecase.NewPartnerUseCase(request.Context())`. Handle constructor errors before calling a use-case method. Do not eagerly construct request-bound use cases in `main`, route wiring, or the controller constructor, and do not inject preconstructed use-case instances or a production use-case factory into controllers. Supply any required non-repository dependencies to the use-case constructor; preserve request cancellation, deadlines, and trace propagation. For controller tests, use a narrowly scoped test seam or isolated dependencies without changing the production construction path.
- `models/`: Go structs representing database tables used by the requested feature, based on the authoritative SQL schema and migrations. For the aggregator, place them in `agregator-backoffice/backend/models/`. Use CamelCase filenames such as `Operator.go`, reuse existing models, and preserve UUIDs, exact monetary types, nullable fields, and relevant column mappings. Define the model-specific data-access interface in the same file as its table model; for example, `models/User.go` declares `User` and `type UserRepo interface` with `GetUserByID`; similarly, `models/Player.go` declares `type PlayerRepo interface`. Name each model-specific interface `<Model>Repo`. Include only methods required by the task; repository methods do not take a context parameter because the repository constructor receives the operation's context. Use parameter and return types consistent with the model and schema. Add or update only the table models needed for the task. Do not expose sensitive fields automatically through HTTP responses.
- For each table model created, define a constructor in its `models/<Model>.go` file named `New<Model>` that returns a new model instance, for example `NewPlayer() *Player`. Accept parameters when needed to initialize required model fields, preserving their schema types and nullability; do not require a context or access the database solely to construct a model. Repository and use-case constructors retain their own context requirements. For each table model created or changed, define getters and setters for its fields as methods in the same `models/<Model>.go` file, using names such as `GetID()` and `SetID(id)`. Preserve the schema's exact field types and nullability; use pointer receivers for setters. Keep compatibility with existing database mapping and serialization, and do not automatically expose sensitive values in HTTP responses or logs. Model accessors must not execute database queries or replace business validation in use cases.
- `repo/`: model-specific repository implementations and data access. Name each implementation with the model name followed by `RepoImpl`, for example `PlayerRepoImpl` in `repo/PlayerRepo.go` and `AdminRepoImpl` in `repo/AdminRepo.go`. Provide a constructor named `New<Model>Repo`, such as `NewPlayerRepo(ctx context.Context)`, that requires a non-nil `context.Context`, obtains the initialized database or pool directly by calling its getter in `internal/Connection.go` (for example `internal.GetPostgreSQL()`), and returns a new implementation of the corresponding model-specific interface. The ordinary constructor must not accept a database or pool parameter; return getter errors explicitly and never open a connection or read connection state directly. Bind the constructor's context to that instance and use it for every database operation; methods such as `GetPlayerByID(id)` do not accept another context argument. Instantiate the repository for each request or operation using its actual context; never share a request-bound instance across requests, substitute `context.Background()` for the caller's context, or retain it past cancellation. Preserve deadlines, cancellation, and trace propagation. For transactional work, bind the same operation context and transaction handle to the required repositories so their queries remain atomic. For example, `repo.PlayerRepoImpl` implements `models.PlayerRepo`; each repository maps database results to the relevant model type. All database queries, including reads, writes, joins, and transaction-scoped queries, must be located in model repository implementations in `repo/`; controllers, use cases, models, views, and routes must not issue SQL or call the database directly. Create each needed repository inside the use-case function via `repo.New<Model>Repo(usecase.ctx)` and handle errors. Do not inject preconstructed repository instances into the use case. For tests, use isolated database handles or a narrowly scoped test seam that substitutes repository constructors without changing the production path; test construction errors and propagation of a canceled or expired context to database calls. Interfaces for other dependencies may be defined near their consumers.
- `internal/`: shared use-case interfaces and supporting implementation such as infrastructure, authentication, and dependency wiring as appropriate. Define the main application configuration struct in `internal/Config.go` at the backend module root, for example `agregator-backoffice/backend/internal/Config.go`. Inspect the existing `configs/config.json` and group configuration structs according to its actual sections and nested fields. Put each relevant component-specific struct in a corresponding CamelCase file in `internal/`, for example PostgreSQL configuration in `internal/Postgresql.go` and Redis configuration in `internal/Redis.go` when those sections are present. The main configuration struct composes those types, with JSON tags and field types matching the actual file. Do not invent or remove configuration sections during a structural refactor; if a component is absent, do not create its struct unless the task requires adding it. Apply the same grouping to other related structs when appropriate. Implement the configuration-loading function and a getter for the successfully loaded configuration in `internal/Config.go`; load and validate `configs/config.json` once during application initialization, and have the getter return the loaded configuration without re-reading the file. Define behavior before a successful load explicitly rather than returning an apparently valid zero-value configuration. Ensure concurrent access is safe and callers cannot mutate shared configuration through returned maps or slices; never log or expose secrets through the getter. Component-specific validation may live in the corresponding `internal/` files. Preserve strict decoding, safe errors, and existing security checks. Keep secret values outside tracked configuration files and do not embed deployment-specific secrets in the structs or source. Declare each use-case interface here and implement it in the matching `usecase/<Tag>Case.go` file. Keep interface method signatures aligned with the relevant OpenAPI operations and use shared request/response types as appropriate. Ensure the `internal` package never imports a use-case implementation and avoid import cycles, especially when model packages use `internal/Const.go`. Keep each operation-specific request struct in the same `internal/` file as its use-case interface, as described below; shared definitions may use `Request.go` when needed. For new backend projects, create the shared API response in `internal/Response.go` as required in the API response contract below. Define reusable global error values and safe error messages in `internal/Errors.go` at the backend module root; for the aggregator this is `agregator-backoffice/backend/internal/Errors.go`. Reuse those values across packages and wrap errors with `%w` where appropriate so `errors.Is` works. Do not include secrets, raw database errors, tokens, or sensitive data in messages returned to clients. Keep HTTP status selection in the controller and response rendering in `view/`. Put all project-defined Go constants in the single file `internal/Const.go` at the backend module root; for the aggregator this is `agregator-backoffice/backend/internal/Const.go`. Define that file as a dependency-free `internal` package and export constants needed by other packages to avoid circular imports. Do not move secrets or runtime configuration into constants.
- `internal/Connection.go`: implement setup for all database connections required by the application in this file, using the loaded configuration and externally supplied credentials. Provide getters in the same file for each initialized database or connection pool, for example `GetPostgreSQL()`, returning the existing handle and an explicit error if initialization failed, has not completed, or the connection has been closed. If a database and its pool or connection are distinct handles in the chosen driver, provide appropriately named getters for the handles the application uses. Getters must not open new connections, expose credentials, or silently return nil; synchronize initialization, access, and shutdown to avoid races. Initialize connections during application startup and report failures without exposing secrets. Implement a `CloseConnections` function in this file to close all active database connections and pools owned by the application, including resources created before partial initialization failure. Invoke it during application shutdown after stopping work that uses the connections. Make repeated or concurrent calls safe, attempt to close every resource even if one close fails, and return or report errors safely when the driver exposes them. Once closed, getters must report that the handles are unavailable. Repository constructors must call these getters directly to obtain database handles; do not execute application queries here, as all queries belong in `repo/`. Configure only databases required by the application and avoid creating additional connections per request. Test access before initialization, after successful setup, and after failure or shutdown, as well as closing multiple connections, repeated close, and concurrent access where relevant.

For each use-case operation, construct only the model repositories needed in the branch being executed, directly in that use-case function. For example, in the operator branch call `operatorRepo, err := repo.NewOperatorRepo(usecase.ctx)`, check the error, and then invoke its methods. Do not create an unused provider repository for an operator request. The constructor is called for each request or operation and obtains the database through the connection getter; never create a new pool per request. Repository interfaces remain declared in `models/`, and SQL remains in `repo/`. For transactions, use an explicit transaction-bound repository constructor with the same operation context and transaction, so all changes remain atomic.

For normal database access, each request-scoped repository constructor itself must call the initialized connection getter in `internal/Connection.go` (for example, `internal.GetPostgreSQL()`); do not obtain the pool in `main` or other dependency wiring and pass it as an argument. Handle getter errors explicitly; never open a separate connection or access connection state directly. For transaction-scoped access, provide a separate constructor that requires the operation context and an existing transaction handle created from the getter-provided connection; do not replace that handle with a new pool or transaction. Tests may use fakes or isolated test handles, without changing the production constructor requirement. All application SQL remains in repository implementations.
- `testcase/`: exclusively test business logic implemented in `usecase/`. Place every use-case test file and its dedicated helper files directly in the root `testcase/` directory, without feature, tag, or other subdirectories; distinguish files using their names, for example `PartnerCase_test.go`. Call exported use-case functions directly, bypassing controllers and HTTP routing. Do not put controller, middleware, routes, view, configuration, repository, or other non-use-case tests in `testcase/`. When those tests are needed, place them alongside their respective packages using Go-compatible `_test.go` files; place cross-package integration tests outside `testcase/` in a dedicated integration test location. Use fakes or isolated dependencies as needed.

These folders describe responsibilities, not a requirement to create empty placeholders.

## Main initialization order

In the application entry point's `main` initialization flow, perform these steps in order: (1) load and validate configuration, (2) open the required database connections, (3) set up OpenTelemetry, (4) set up routes and their dependencies, and (5) set up and start the server. Stop initialization on an error; clean up every resource that was successfully initialized, including database connections if a later step fails. On shutdown, stop the server and in-flight work before closing database connections, and flush or shut down telemetry safely. Since database initialization occurs before OpenTelemetry setup, do not claim that its startup failures are covered by an OpenTelemetry trace; report them safely through startup logging.

## Interface implementation constructors

Every project-defined interface implementation created or modified, except controllers, must have a constructor named `New<Implementation>` or the domain-specific constructor name required above, such as `NewPlayerRepo` or `NewPartnerUseCase`. Construct instances through that constructor, including implementations of infrastructure and external-service interfaces; inject required non-repository dependencies and validate required inputs. Model repositories are created inside the use-case function as specified above. Use a request or operation context in constructors for use cases and repositories as specified above; other implementations receive a context when their lifecycle requires one. Scope context-bound instances to the operation and preserve cancellation and tracing. Third-party implementations are used according to their own APIs. Do not add unrelated interface implementations or change their behavior solely to apply this rule.

For every API operation in the requested OpenAPI contract, declare an operation-specific request struct in the same `internal/` file as its use-case interface, for example `RequestGetPartner` alongside `PartnersUseCase`. The controller decodes and validates the applicable request body, path parameters, query parameters, and headers into that struct, preserving OpenAPI types, required fields, nullability, and content types; an operation without request fields still has its own empty request struct and must not decode a nonexistent body. The controller then maps the validated request into the corresponding `Param` struct. Never accept identity, authorization, or tenant scope from untrusted request fields as a substitute for middleware-provided trusted context. For all operations in the requested API contract, declare the corresponding use-case method in an interface under `internal/` and implement it in the matching `usecase/<Tag>Case.go` file, following the operation ID and the response rules below. Track coverage against the specification, implement real dependencies where required, and report missing operations or external integrations explicitly; do not mark placeholder, mock, or unimplemented methods as completed. Preserve endpoint-specific transport representations and avoid import cycles.

Every business use-case function must accept its operation input in a single operation-specific struct named `Param` followed by the exported function name, for example `GetPartner(param ParamGetPartner) (*DataGetPartner, error)`. Declare each parameter struct in a shared package accessible to the interface, implementation, and controller without import cycles; include only input fields required by the operation, preserving their types and validation semantics. Use a dedicated struct for each operation, even where fields overlap. For an operation with no input fields, use an empty operation-specific parameter struct. Infrastructure parameters such as an existing method-level `context.Context` remain separate when required to preserve caller context; constructors continue to require context and required non-repository dependencies as specified above. Controllers validate transport input and map it to the parameter struct; do not allow a caller-provided field to substitute for trusted identity or authorization context. Update the interface, implementation, fixtures, and callers together.

Every business use-case function must return exactly one result data value and one `error`, including read and write operations. Do not return multiple independent business data values; group related results in the single operation-specific result struct. A constructor returns its constructed instance and an error, and test fixture helpers are not business use-case operations. Name the operation-specific result struct `Data` followed by the exported use-case function name: for example, `GetPartner` returns `(*DataGetPartner, error)`; `ListPartners` returns `(*DataListPartners, error)`. Declare the result struct where the use-case interface and controller can share it without import cycles, and preserve the exact OpenAPI data shape and JSON field names. Apply this naming to the struct carrying the result for each operation, not to database table models or the shared `ResponseAPI` envelope. If the OpenAPI success data is a scalar or array that cannot be represented as a struct without changing its JSON shape, preserve the contract through an appropriate named result representation or serialization; do not silently change the wire format. Declare the same return contract in its interface under `internal/` and implement it in `usecase/<Tag>Case.go`. On success, return a non-nil pointer to the actual meaningful result and a nil error; after handling errors, the controller places that result directly in `ResponseAPI.Data` without a redundant `data == nil` check. The use case must report missing or empty data as an appropriate error. On every error path, return `nil` as the data together with the appropriate non-nil classified error, including wrapped errors and canceled contexts. Do not return HTTP status codes or the `ResponseAPI` transport envelope from the use case. Declare the same pointer return type in the interface, implementation, mocks, and callers, and test both the non-nil success result and nil result on failures. For an existing interface, update affected callers within the requested scope and report any external compatibility impact. The use case ensures that the successful result is not empty under the rule below; the controller relies on the use-case return contract. If an OpenAPI operation defines no success data, record the mismatch and resolve the contract within the authorized scope rather than inventing a result or claiming compliance.

## API response contract

For every Go project with an HTTP JSON API implemented using this skill, create a shared JSON response view at the project module root in `view/Json.go`, following the user-provided `testbackend/view/Json.go` example. Expose `Json(writer http.ResponseWriter, status int, body internal.ResponseAPI)` so controller-owned handlers and rejecting middleware pass their chosen status and shared response directly to it. The view marshals the supplied `ResponseAPI` to JSON, sets `Content-Type: application/json` and `Cache-Control: no-store`, and writes the supplied status and encoded body. It does not inspect the supplied status, validate business data, invoke use cases, or access the database. In `view/Json.go`, define two package-level `[]byte` variables exactly as in the example: `ResponseEncodingFailed` contains `{"message":"encoding response failed"}`, and `ResponseWriteFailed` contains `{"message":"response write failed"}`. Use the corresponding variable for each fallback response; these are variables because Go does not permit slice constants. For fallback writes whose return values are intentionally discarded, call `writer.Write(ResponseEncodingFailed)` or `writer.Write(ResponseWriteFailed)` directly; do not use assignments such as `_, _ = writer.Write(...)`. Continue checking the error from the normal response write so the write-failure fallback is triggered. Follow the error-handling behavior shown in `testbackend/view/Json.go`: marshal before writing the normal response; if marshaling fails, attempt to return HTTP 400 with the safe JSON body `{"message":"encoding response failed"}` and stop. If writing the normal response fails, attempt to write HTTP 400 and the safe JSON body `{"message":"response write failed"}`, as in the example; do not expose raw errors. Once HTTP headers or bytes have already been sent, the second status cannot replace the original status and the fallback body may not reach the client or form valid JSON; treat this as best effort. Do not use `slog` or other direct application logging in `view.Json`: error monitoring uses the project's OpenTelemetry setup. Do not claim OpenTelemetry automatically records a rendering error when the view lacks a request context or explicit instrumentation; report that limitation or instrument it through an authorized context-aware integration without changing the required view signature silently. Test both failure paths with a response writer that reports errors as well as normal responses. A Go project without an HTTP JSON API does not need an unused HTTP view. Test the response bodies and supplied status through controller and middleware paths.

For every new backend project, define and use a shared `internal.ResponseAPI` in the backend module root at `internal/Response.go`, following the reference `agregator-backoffice/backend/internal/Response.go`: exported fields `Data any`, `Message string`, and `TraceID string`, with JSON names `data`, `message`, and `trace_id`. Controllers and middleware must prepare all API response bodies using this shared type and pass them to the view; do not create ad hoc response envelopes per endpoint. Do not create response helper or constructor functions such as `NewDataResponse`, `NewMessageResponse`, or `NewTraceResponse`; declare a local `var respAPI internal.ResponseAPI` and assign `respAPI.Data`, `respAPI.Message`, or `respAPI.TraceID` directly before calling `view.Json`. Apply the same direct-field pattern to middleware rejection responses. Preserve the exact status-specific JSON shapes below while preserving the reference fields. A 200 response requires non-empty `data`: treat nil (including typed nil), an empty or whitespace-only string, and an empty array, slice, or map as empty and return 400 with a safe message instead. Boolean false and numeric zero are valid data and must remain present. Handle empty data through the use case error and the controller before calling the view; do not introduce response constructors or response-layer validation helpers. For OpenAPI operations whose documented success body allows empty collections or null, flag and resolve the contract mismatch within the authorized scope rather than silently claiming compatibility. Select the response variant in the controller or middleware, not in the view, and do not make the view inspect the HTTP status or infer the body shape. Retain endpoint-specific data structures as the value of `Data`. Test serialization and controller/middleware responses for 200, 400, and 500, including empty-data 400 cases and successful false and zero values, and check that no extra fields are emitted.

In each controller, declare the operation-specific request struct variable with `var` and name it exactly `req`, for example `var req internal.RequestGetPartner`. When assigning request values, set each property individually in a separate statement; for example, `req.PartnerType = request.PathValue("partnerType")`. Decode request bodies into `&req` when the contract requires a body. Do not initialize the request DTO with a struct literal or `:=`; use `req` when validating and mapping input to the use-case parameter. Declare the local variable holding the operation-specific use-case parameter with `var`, naming it with the `param` prefix followed by the exported function name, for example `var paramGetPartner internal.ParamGetPartner` for `GetPartner`. Assign each field individually on separate statements, for example `paramGetPartner.PartnerID = id`, and pass that variable to the use-case method. Do not initialize the parameter with a struct literal or `:=`. This naming rule applies to the request DTO, not the `*http.Request` handler argument. Controllers must decode and validate request input before creating or invoking a use case: check required fields, formats, UUIDs (including nil UUIDs when prohibited), and allowed enum values against the API contract, and return HTTP 400 with `"invalid input"` when validation fails. Do not repeat request validation in a use case: for example, a `GetPartner` use case must not check `param.PartnerID == uuid.Nil` or validate the `PartnerType` enum. Use cases operate on validated parameters and implement business logic, including decisions based on data retrieved during that logic; this is distinct from validating the incoming request.

Define two exported Go error types, `internal.InternalError` and `internal.InputError`, in the backend module root `internal/Errors.go`; both implement `error`. Every non-nil error returned by a business use-case method must be one of these two types, including failures received from repositories or external dependencies. Return `InputError` for user-caused business outcomes discovered while executing the business logic, such as data not found or incorrect credentials; do not use it to duplicate controller request validation. Return `InternalError` to the controller only for application-internal or dependency failures, such as a failed database or external service, network failure, or timeout. Do not classify user-caused business outcomes such as missing data or incorrect credentials as `InternalError`; return `InputError` for those outcomes. Return nil data with either error. Preserve underlying causes through `Unwrap` where useful, without exposing sensitive details to clients. Controllers classify the use-case error with `errors.As`, mapping `InputError` to HTTP 400 with a safe message and `InternalError` to HTTP 500 with only the correlated trace ID. Handle an unexpected unclassified error as HTTP 500; never infer classification from message text. This rule concerns the use-case method boundary; repository and infrastructure internals may use their own errors before translation. Test both categories, wrapped causes, nil data on errors, and controller mapping.

For API specifications and implementations created or changed within the requested scope, use only HTTP status codes `200`, `400`, and `500`, including responses from middleware and HTTP adapters. In the controller, return `200` when the invoked use case succeeds; return `400` for input validation failures, data not found, and other explicitly identified errors caused by the user or their request; return `500` for unexpected internal or dependency failures. Classify known errors using safe typed or sentinel errors and `errors.Is`/`errors.As`, including wrapped errors; never classify errors by matching their message text. Translate database no-row results to a domain not-found error in the repository. Do not expose raw database or infrastructure errors to clients. ## Go function formatting

In newly created or modified Go functions and methods, put the body on a new line after the opening `{` and leave one blank line before the first statement. Also leave one blank line after the opening `{` of a conditional block, including each `if`, `else if`, and `else` body, before its first statement. After a complete control-flow block such as `if`, `for`, `switch`, or `select`, leave one blank line before the next statement. Leave one blank line after a standalone function-call statement or assignment whose right-hand side is a function call, before the next statement. Preserve Go syntax: keep `else` attached to the preceding `}` as required, and do not insert a blank line before a closing `}` or inside a multiline call. Keep error handling and control flow correct. Run `gofmt` on modified Go files, and do not reformat unrelated files solely to enforce this style.

After each complete function or method declaration, leave one blank line before the next declaration. Likewise, after a `}` that completes a block, leave one blank line before the next independent statement or declaration. Do not separate `} else {` or other syntactically connected parts, insert a blank line before an enclosing `}`, or split composite literals and multiline expressions.

Do not use the Go `if` initializer shorthand to call a function or assign an error, such as `if err := doWork(); err != nil`. Call the function or assign the error in a separate statement, then check it with `if err != nil`, preserving error handling and the blank line after the call as specified above. Apply this to project-created or modified code, including tests, without refactoring unrelated code.

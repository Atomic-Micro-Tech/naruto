# First Naruto campaign stage: economy audit

The executable campaign table0 at80058758 selects **scenario0** for stage0. Scenario record80057798 gives map0, modeFlags0, roster character12/10,1500 initial chakra,3000 target,400 base source bonus,3 initial skill and4 skill per completed source bonus. These are a two-player ordinary-mode match. Character12 is the tutorial/early variant; replacing it with character0 changes original techniques/CPU fields. Existing browser scenario0 initialization retains the correct roster and values.

## Prioritized mismatches seen in browser implementation

1. `engine.js` paid tolls immediately and ended the turn without the original forced-sale branch. `800dc2e0` case2 saves pre-clamp post-toll projection in board+4f0. Case7, after payment, requires sale only if that projection is negative, owned type5 barriers exist, and mode1 is clear. `800e03b0` enters selection; `800d15a8` confirms/sells repeatedly until recovered or no barriers remain. **Do not globally eliminate a negative-chakra player in scenario0.** Do not automatically force-sale every negative balance caused by a chance card or technique cost; preserve the toll branch trigger.
2. Remote upgrade from source/crystal selection cases3/8 in `800d15a8` increments exactly one level and one HP and queues negative base upgrade cost. The browser exposed all higher levels for the same remote menu. Multi-level nonlinear prices belong to the owned-barrier menu. `800edd68` enters optional remote upgrade case8 after a successful source bonus even with remaining movement, and resumes movement afterwards. The browser initially skipped that interruption when passing the source.
3. The original chakra counter is queued and animated, not an instantaneous total change. `800be5d8` consumes units, then tens, then hundreds, etc. One initialization update precedes payment ticks. All player queues advance together per board update, gated by the original pause/modal condition (`800b2a58`, call at BOARD.c3217). Bankruptcy/turn changes wait for zero queues. The helper preserves non-team arithmetic, clamps and debt-crossing events; it does not reproduce HUD sprites/sounds.
4. CPU enemy-barrier choice used a guessed `chakra>300 && rent>70`. The actual decision is `800f1290` case4, recovered separately in `story1-cpu.mjs`. See its documentation. Attack availability excludes zero costs when calculating minimum; inventory card22 halves the minimum and can mark compulsory card use. Original first4 selection pruning happens later.

Win/lose behavior already supported by the source-bonus helper: `800edd68` case3 tests settled wallet against3000 **after a complete crystal lap pays its bonus**, before optional upgrades/scroll award. Merely reaching3000 from chance/toll income elsewhere does not end the match. Both participants can win at their source visit; the campaign then takes success/failure according to human winner. Scenario0 has no round limit and no negative-balance elimination flag. A player with no barriers can remain in debt and continue toward the source.

## Native helper contract

`story1-economy.mjs` uses the same `{players,tiles,modeFlags}` shape as `board-effects.mjs`. Existing extractor `unknownValues[0]` is runtime tile ushort+1c; `[1]` is+1e, confirmed by map loader800f8xxx (BOARD.c27233–27239). Therefore no new asset extraction is needed.

* `saleValue(tile)` = signed16(`saleBase + (level−1)*saleIncrement`), accepting explicit fields or `unknownValues`. This is **not** purchase price, upgrade spending, rent or a guessed percentage.
* `forcedSaleRequired(state,actor,{projectedChakra})` is the toll-only transition check. Supply captured post-toll projection, not an unrelated later balance.
* `forcedSaleCandidates(state,actor)` returns all owned type5 barriers in original table order as `{tile,value}`. Human chooses a barrier and confirms the sale. `cpuForcedSale(state,actor)` chooses the first strict minimum of original chain-adjusted rent + chainExtra×2000 (`800e0298`), with no RNG.
* `commitBarrierSale(state,actor,tileId)` returns copied state, signed saleDelta, projectedChakra, `needsAnotherSale` and remaining candidates. It is an atomic logical commit after original animation. Never apply the payment queue again to this result. Tile becomes type4 with packedwordf020: owner15, level1,HP2,effect0. **Repair counter tile+6 is preserved here**, unlike elimination reset. Effect-owner byte is preserved. If debt remains but no barriers do, continue the turn; no invented bankruptcy ending.
* `remoteUpgradeChoices` returns each owned nonmax barrier's sole next level/base cost; `commitRemoteUpgrade` applies that one-level mutation atomically. Resume the interrupted source/crystal state after confirmation; do not always end the turn.
* Optional `startChakraPayment(chakra,delta)`/`tickChakraPayment(payment)` port the non-team queue's arithmetic at update granularity. Tick once per eligible board update, first tick initialization. Return `done`, `ticks`, `crossedIntoDebt`. Do not double-apply with atomic commits. Team mirroring is deliberately outside scope. Exact short delta−32768 overflows original magnitude storage and is rejected explicitly.

Tests: `node --test research/story1-economy.test.mjs` (9 cases). These verify source constants, sale pricing/ownership/continuation, queue stepping/clamp, remote upgrade, and mutation isolation. They do not establish full visual/audio/story parity.

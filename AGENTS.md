# Project agent instructions

When implementing or modifying backend features in this repository, read and follow [.agents/skills/api-creator/SKILL.md](.agents/skills/api-creator/SKILL.md). It specifies the project's SOLID and MVC approach, uses the folder layout in `backendexample/` as the reference, including root-level `models/` and `repo/`, and requires business use cases to be grouped by OpenAPI tag under `usecase/` at the target backend Go module root (for aggregator backoffice: `agregator-backoffice/backend/usecase/`). Before implementing a use case, create representative synthetic mock data from the relevant OpenAPI contract in `usecase/MockData.go`; use it for direct tests and never silently return it as production data. Define tag-specific use-case interfaces in `internal/<Tag>.go` and implement them in `usecase/<Tag>Case.go`, avoiding import cycles; for tag `Partners`, use `internal/Partner.go` and `usecase/PartnerCase.go`. This convention applies to every tag in the applicable API specification; `Partners` is only an example. For every operation in the requested API contract, define an operation-specific request struct in the same file as its use-case interface, and implement its interface method in the corresponding `usecase/<Tag>Case.go` file. Controllers decode and validate the applicable body, path, query, and headers into that request struct before mapping it to the use-case parameter. Each business use-case function accepts one operation-specific `Param` struct named after the function, such as `ParamGetPartner`, with required context kept separate, and returns exactly one actual result data pointer and one error; on any error return nil data, while success returns non-nil data and a nil error; group related results in that single data value; name its result struct with the `Data` prefix followed by the use-case function name, such as `DataGetPartner` for `GetPartner`, while preserving the API JSON shape; the controller places successful data in `ResponseAPI.Data`, while the use case does not return HTTP status or a response envelope. Place database table models and their model-specific data-access interfaces in the corresponding file in the backend root `models/` directory, aligned with the SQL schema and migrations; name each interface `<Model>Repo` (for example, `type PlayerRepo interface` in `models/Player.go`) and implement it in `repo/` using `<Model>RepoImpl` (for example, `repo.PlayerRepoImpl` in `repo/PlayerRepo.go`). Place all database queries, including joins and transaction-scoped queries, in model repository implementations under `repo/`; use cases access data through repository interfaces. Each use-case function creates only the repositories needed for the active branch by directly calling the appropriate `repo.New<Model>Repo` constructor with the use-case context and handling its error; do not inject preconstructed model repositories into use cases. The repository constructor obtains its connection through `internal/Connection.go`. Preserve transaction-bound constructors for atomic operations and use test seams or isolated databases as needed. Register all HTTP routes in `routes/Routes.go` and implement common HTTP middleware in `middleware/Middleware.go` at the backend module root. Define `NewRoutes` as in the provided example: create a ServeMux, register the matching controller handlers, and return it wrapped in `otelhttp.NewHandler(mux, "/")` as an `http.Handler`; protected routes still require appropriate middleware. Use the HTTP flow `routes → middleware → controller`: each route passes a named controller HTTP handler directly to middleware, and middleware directly calls that handler only after its checks succeed. Authorizer creation, authentication, authorization policy and tenant-scope checks belong in middleware, not routes. Route registration must not check whether an authorizer is nil or select scopes; initialize required dependencies before serving and fail closed for missing dependencies or unmapped protected operations, while explicitly allowing intended public routes. A controller constructor is not required; use named package-level handlers where appropriate. Follow the direct HTTP handler pattern in `HandleGetPartnerExample`: the named controller handler declares a request-local `var respAPI internal.ResponseAPI` before request validation and assigns its fields directly without `NewDataResponse`, `NewMessageResponse`, or `NewTraceResponse` helpers, then performs request decoding, validation, use-case invocation and response selection. For invalid input assign `respAPI.Message = "invalid input"` directly and render HTTP 400 through `view.Json`; do not create a constant for this message. render the same shared response type on every other response path. Do not split controller operations into typed response methods plus HTTP adapters, or wrap handlers in generic adapters or anonymous functions in the route file. Define a shared exported `telemetry.Tracer` in `telemetry/Telemetry.go` using `otel.Tracer` with the exact module path from `go.mod`; start controller spans with it and propagate their context; follow the actual OpenAPI request shape, including no body where none is specified. After decoding and validating input, each controller operation constructs its required use case directly with its constructor and the request context, checks the constructor error, and then invokes the use case; when construction fails, assign `respAPI.Message = "invalid context"` directly and render HTTP 400 through `view.Json` before returning; do not inject preconstructed request-bound use cases or production use-case factories into controllers. Controllers select HTTP status: 200 for use-case success, 400 for input validation, missing data and other explicitly identified user-caused errors, and 500 for unexpected internal or dependency errors. Classify wrapped errors with errors.Is or errors.As and return safe messages. Middleware handles authentication and authorization, use cases contain business logic, and views render responses. For Go HTTP JSON APIs, put the shared response renderer in `view/Json.go` as `Json(writer http.ResponseWriter, status int, body internal.ResponseAPI)`; it renders the supplied status and body without validating them and follows the `view.Json` example for encoding and write errors, including best-effort HTTP 400 fallback; define `ResponseEncodingFailed` and `ResponseWriteFailed` as `[]byte` variables in `view/Json.go` and use them for their respective fallback bodies. Call fallback writes directly, for example `writer.Write(ResponseEncodingFailed)`, without `_, _ =`; retain error checking for the normal response write. Do not use `slog` or other direct logging in `view.Json`; error monitoring uses OpenTelemetry, and do not claim that rendering errors are traced without context and instrumentation. Reserve the backend root `testcase/` directory for testing use-case business logic directly, bypassing controllers and HTTP routing; put all use-case test files directly in `testcase/`, without subfolders. Put non-use-case tests outside `testcase/`, alongside their respective packages, and use a dedicated location outside `testcase/` for cross-package integration tests. Define the main application configuration struct, loading function, and getter for the successfully loaded configuration in `internal/Config.go` and group component-specific structs in separate CamelCase files according to the sections actually present in `configs/config.json`; load values from that file and do not invent sections during a structural refactor. Define reusable global error values and safe error messages in `internal/Errors.go` at the backend module root; never return raw sensitive errors to clients. Put project-defined Go constants in `internal/Const.go` at the backend module root and use CamelCase Go filenames, retaining required `_test.go` and build suffixes. Apply it within the requested backend scope; do not restructure unrelated code solely to match the suggested layout.

These instructions are for any contributor or AI agent that reads `AGENTS.md`; tools that support project skills may also invoke the skill as `api-creator`.
